# 热修复与回滚

## 什么时候发新补丁版本

只要已公开 JAR 的行为、存档或依赖发生变化，优先发布新 patch 版本，不静默替换旧文件。用户和整合包需要可验证、可回滚的 artifact。

## 允许替换资产的情况

仅在发布明显上传错误、尚未广泛分发且维护者明确决定替换时操作；文件名增加 `hotfix` 仍不能解决相同版本不同内容的可追溯问题，因此 Release notes 必须记录旧/新 SHA-256 和时间。

## 流程

1. 建最小复现测试。
2. 在 main 修复、测试并提交。
3. 明确要求后同步其他版本。
4. 构建 clean JAR，记录 SHA-256。
5. 发布新 patch，列出受影响版本、风险和迁移步骤。
6. 旧版本标记为有问题但保留，除非存在安全/法律原因。

## 存档回滚

持久化格式变化必须带 schema 和向前迁移。无法向后兼容时在发布前备份世界，并提供解绑/导出命令。ReturnBuffer 和在途任务绝不能因版本迁移静默丢失。
