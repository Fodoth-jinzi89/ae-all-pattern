# 限制、风险与非目标

## 为什么不能“JEI 有配方就全部自动支持”

JEI 知道如何展示配方，却通常不知道：

- 机器从哪一面接收哪种材料；
- 哪个槽是催化剂，是否消耗；
- 机器忙碌时能否继续插入；
- 概率副产物如何向 AE 声明；
- 输出怎样回到网络；
- 专用服务器没有 JEI 时如何工作。

因此 JEI 只能做显示与开发辅助，不能替代机器适配器。

## 第一版明确过滤

- 概率小于 100% 且没有确定性建模策略的输出。
- 结果依赖输入 NBT/组件但配方 API 无法给出确定结果的配方。
- 需要玩家、环境、红石序列或世界方块参与的处理。
- 会消费或产生流体、气体、化学品但适配器尚未声明支持的配方。
- 输入与输出构成递归复制、可能让 AE 合成规划失稳的配方。
- 单个绑定超过配置上限的样板，超出部分记录在诊断信息中。

## 运行风险

- 数千配方同时刷新可能产生单 tick 尖峰：必须在重载阶段建立索引并做增量 diff。
- 目标机器被外部物流抢占可能令投料失败：`pushPattern` 必须允许返回失败并稍后重试。
- 输出未回 AE 时，AE 合成任务会等待：文档和 UI 必须明确返回路径。
- 网络权限改变后旧绑定不能继续操作：每次重要操作都重新服务端校验。
- 模组升级可能改变机器类或 RecipeType：绑定记录含 schema 与目标类型指纹，失败时安全离线。
