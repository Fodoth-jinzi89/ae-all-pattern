# 代码复用、继承、组合与反射

## 选择顺序

1. 使用上游公开 API 和事件。
2. 组合公开服务对象。
3. 实现公开扩展接口。
4. 继承文档明确为扩展点的稳定基类。
5. 小范围、可隔离、有保护的反射。
6. Mixin/访问转换只在没有公共路径且收益明确时考虑。

不要因为“原版机器已经做过类似逻辑”就继承内部实现类。继承会一起带入生命周期、字段布局、同步和升级假设；组合 `IManagedGridNode` + `ICraftingProvider` 更接近 AE2 公开意图。

## 阅读源码的方法

- 从接口 Javadoc 反查实现，理解调用顺序和不变量。
- 只复用行为契约，不复制大段实现。
- 对照专服与客户端入口，确认类加载侧。
- 查看上游自己的测试，了解异常、重载和持久化边界。
- 记录使用到的非稳定 API，并集中封装在 compat 包。

## 适合继承

- NeoForge/MC 明确要求扩展的 `Item`、`Block`、`BlockEntity`。
- 上游公开且文档承诺供附属扩展的抽象类。
- 子类真正满足父类语义和生命周期。

## 适合组合

- AE Grid Node 与 crafting provider 服务。
- 机器能力和输入事务。
- 配方索引、缓存、诊断。
- 第三方模组可选兼容。

## 反射保护

若为未知附属做探测：

- 使用访问集阻止父子类型循环。
- 深度上限 64，候选数量和耗时有预算。
- 捕获 `LinkageError` 与可预期运行时异常。
- 失败只禁用当前适配器，不能拖垮所有配方索引。
- 记录一次清晰日志，不在每 tick 重复刷屏。

Mekanical Create 曾因递归收集配方类型触发 `StackOverflowError`；这一类错误应由结构上限和单元测试预防，而不是只靠玩家复现。
